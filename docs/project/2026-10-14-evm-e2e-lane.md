# evm-e2e lane：真实发日志与 reorg 实际未验收

- 日期：2026-10-14
- 对应 §10 行：*"契约、Anvil端到端与依赖健康检查**不空跑**；必需skip=0，未知skip=0"*
- 对应 lane 定义（§7）：`evm-e2e` — *"本地双 Anvil、**真实发日志**、单体/四服务核心场景、**reorg/restart**"*，验收 *"oracle/DB/API 摘要一致；依赖缺失直接失败"*
- 证据：`build/acceptance/<sha>/e2e-lane/`
  - `e2e-full-run.jsonl`（本地完整跑，344 个顶层用例）
  - `ci-anvil-simulated-absent.jsonl`（按 CI 条件模拟）
  - `SUMMARY.txt`

## 结论

**Go 的 `test/e2e` lane（也就是 CI 实际跑的 lane）没有验收"真实发日志"与"reorg"。**
其中 29 个用例**在任何环境下都必然 skip**——包括 CI——因为它们依赖一个硬编码的占位 DSN。
真正会发日志、做真实 reorg 的验收**存在**，但在 `docker/` 脚本里，而**没有任何 CI lane 会跑它**。

三条独立的缺陷叠在一起，任何一条都足以让这个 lane 名不副实。

---

## 缺陷 1：29 个用例无条件 skip（含发日志与 reorg 两个）

本地把 Postgres/Redis 的门都打开、Anvil 也在 PATH 上，完整跑一遍：

```
top-level tests: 344
verdicts: {'pass': 315, 'skip': 29, 'fail': 0}
```

skip 的 29 个按家族分组：

| 家族 | 个数 |
| --- | --- |
| `TestHappyPath_*` | 6 |
| `TestErrorScenario_*` | 6 |
| `TestMultiChainScenario_*` | 6 |
| `TestPerformanceScenario_*` | 6 |
| `TestDataPullerEventCollection`、`TestDataPullerReorgHandling` | **2** |
| `TestOrchestrator_Initialize`、`TestBlockchainManager_Initialize`、`TestDatabaseManager_Initialize` | 3 |

根因在 `test/e2e/orchestrator.go:27`：

```go
func NewTestOrchestrator() *Orchestrator {
	return &Orchestrator{
		blockchain: NewBlockchainManager("http://localhost:8545"),
		database:   NewDatabaseManager("postgres://user:password@localhost:5432/test"),
		api:        NewAPIManager("http://localhost:8080"),
	}
}
```

三个地址全是**硬编码占位值**：

- `postgres://user:password@localhost:5432/test` —— 字面量 `user`/`password`/`test` 库。
  `DatabaseManager.Initialize` 会真的 `pgxpool.ParseConfig` + `pool.Ping`，所以它**必然 ping 失败**。
  CI 建的是 `test:test@localhost:5432/chainpulse_test`，**连 CI 的库也对不上**。
- `http://localhost:8080` —— 没有任何东西在这个端口起 API 服务。

而 **`test/e2e` 包不读任何数据库环境变量**：

```
grep -rhoE 'Getenv\("[A-Z_]+"\)' test/e2e/*.go | sort -u
→ EVM_RPC_ENDPOINTS, MULTICHAIN_REQUIRE_SOLANA, MULTICHAIN_STRICT, SOLANA_RPC_ENDPOINT
```

CI 认真设的 `TEST_DATABASE_URL`、`POSTGRES_HOST/PORT/USER/PASSWORD/DB`、`REDIS_HOST/PORT`
**一个都没被读过**。于是：

> `isDatabaseAvailable()` → `orchestrator.Setup()` → ping 占位 DSN 失败 →
> `t.Skipf("Failed to initialize orchestrator")` → **29 个用例永远 skip**。

这不是"本机没起服务"，是**没有环境能让它们跑起来**。我给了 Postgres 和 Redis 并把门全开，
它们照样 skip——因为没有任何开关能覆盖那个硬编码字符串。

## 缺陷 2：`anvil_test.go` 在两个 CI lane 里都不执行（互补的错误）

`test/e2e/anvil_test.go` 是唯一带 `//go:build e2e` 的文件（另外 40 个 `_test.go` 都没有 tag）。

| workflow / job | 装并起 Anvil？ | `-tags=e2e`？ | 结果 |
| --- | --- | --- | --- |
| `test.yml` → `test`（e2e 步） | **是**（`Install Foundry (for Anvil)`、`Start Anvil`、`Cleanup Anvil`） | **否** | `anvil_test.go` **不参与编译**，装了白装 |
| `ci-integration.yml` → `e2e` | **否**（无 Foundry 步骤，只起 postgres/redis） | **是** | 编译进来了，但 **6 个全 skip** |

第二行我按 CI 条件验证过（临时 `HOME`、PATH 里也没有 anvil）：

```
verdicts: {'skip': 6}   go test exit=0
skip  TestAnvilStartupVerify
skip  TestAnvil_Connect
skip  TestAnvil_FilterLogs
skip  TestAnvil_GetBlockHeaders
skip  TestAnvil_ParentHashChainVerification
skip  TestAnvil_PullerIntegration
```

`startAnvil` 在 `cmd.Start()` 失败时 `t.Skip("anvil not installed — skipping e2e test")`，
`IsAnvilAvailable()` 又只在 `anvil` / `$HOME/.foundry/bin/anvil` / `$HOME/.local/bin/anvil` 里找——
CI 上都不存在，于是 **exit 0、全绿**。

两边的错误正好互补：**能用的 lane 没装工具，装了工具的 lane 没有 tag。**
而正确的命令其实已经写在 Makefile 里了：

```
test-anvil:  ## Run Anvil-based integration tests (requires foundryup, install manually)
	@which anvil > /dev/null 2>&1 || { echo "anvil not found..."; exit 1; }
	$(GO) test $(TESTFLAGS) -tags=e2e -run TestAnvil ./test/e2e/...
```

它同时具备 `-tags=e2e` 与**缺依赖即失败**的检查——正是 §7.4 那条"依赖缺失直接失败"。
**但没有任何 CI lane 调用它。**

## 缺陷 3：lane 内"真实发日志 / reorg"是伪造与模拟

即便那 29 个用例能跑，lane 里另外两个"真实事件"用例也不发真实日志。

`test/e2e/blockchain_manager.go`：

```go
func (bm *BlockchainManager) DeployContract(...) (*DeployedContract, error) {
	deployed := &DeployedContract{
		Address:     fmt.Sprintf("0x%040x", time.Now().UnixNano()),  // 时钟造地址
		TxHash:      fmt.Sprintf("0x%064x", time.Now().UnixNano()),  // 时钟造 tx
		BlockNumber: 0,
	}
	blockNumber, _ := bm.GetBlockNumber(ctx)   // 只读当前块号
	deployed.BlockNumber = blockNumber
	return deployed, nil                        // 从未发送交易
}

func (bm *BlockchainManager) EmitEvent(...) (*EventEmission, error) {
	emission := &EventEmission{ ID: fmt.Sprintf("event-%d", time.Now().UnixNano()), ... }
	// 没有 SendTransaction，没有日志
	return emission, nil
}
```

`DeployERC20DeployCode` 更直白——注释写着"模拟字节码用于测试"，返回的十六进制串里
含 `3670penta` 这种非法字符。

`TestDataPullerEventCollection`（`data_puller_test.go:60`）随后：

1. `DeployContract` 拿到**时钟造的地址**；
2. `EmitEvent` 拿回**造的 EventEmission**（`TxHash` 为空、`LogIndex` 恒为 0）；
3. 再用它**逐字段构造** `CollectedEvent`（`RawData: []byte{}`，空字节）；
4. 调 `ValidateEventCollection(emittedEvents, collectedEvents)`。

而 `ValidateEventCollection` 的键是 `TxHash_BlockNumber_LogIndex`——第 3 步的键**抄自**第 2 步，
所以恒等成立；`TxHash` 为空、`LogIndex` 全 0，5 个键还会**互相覆盖**。这是**同义反复的断言**。

reorg 同理。`data_puller_manager.go`：

```go
func (dpm *DefaultDataPullerManager) SimulateReorg(ctx context.Context, reorgDepth uint64) error {
	// 只改内存里的 collectedEvents 与一个 ReorgSimulation 结构
	// 全程不碰链
}
```

全仓库搜索 Anvil 的真实 reorg 原语：

```
grep -rn "evm_snapshot|evm_revert|EvmSnapshot|EvmRevert" test/ pkg/ scripts/  →  空
```

`TestMultiChainERC20Events` 名字里有"ERC20 Events"，实际只**比对事件签名哈希常量**，
不发事件；`TestMultiChainRealEvents` 只连链读块号与余额。

## 公平的一面：真实路径存在，但没接进 CI

不能因此说"项目从没有真实验收"。真实的那套在 docker 脚本里，而且是**真的**：

- `docker/verify-e2e-reorg.sh` —— `cast rpc evm_snapshot` → 发真实 Ping 事件 →
  `evm_revert` → 核对前后索引数：
  ```
  # Test 1: Reorg Injection via evm_snapshot/evm_revert
  snapshot_result=$(cast rpc evm_snapshot --rpc-url "$RPC_URL")
  ```
- `docker/verify-e2e-indexing.sh` —— 在每条 Anvil 链上**真实部署 EventEmitter** 并发事件。
- `scripts/multi-chain-e2e.sh` —— 真实起多链 Anvil（支持 `--fork-url`），有 Makefile 目标。

问题在于接线：

```
grep -rn "verify-e2e-indexing|verify-e2e-reorg|multi-chain-e2e" .github/workflows/  →  空
grep -rn "make test-e2e|make multi-chain|make e2e" .github/workflows/               →  空
```

- `verify-e2e-reorg.sh` / `verify-e2e-indexing.sh` 只被 `docker/ACCEPTANCE.md` 与归档 spec 引用，**无 Makefile 目标、无 CI**。
- `multichain-e2e-acceptance` 等**有** Makefile 目标，**无 CI**。

所以现状是：**真实的那条路径没人自动跑；自动跑的那条不真实。**

## 与已记录问题的关系

- **D13** 是"`test/acceptance` 没有任何 lane 跑"；本条是"`test/e2e` 跑了，但核心场景在里面 skip"。
  两者是同一个模式的两面：**验收代码写好了，但没接上会变红的回路。**
- **F13**（契约 job 空跑）也是同一族：`--min-tests 1` 挡得住"空套件"，
  挡不住"套件里真适配器全 skip"。e2e 的两个 job 同样**只带 `--min-tests 1`**，
  没有 `--fail-on-unknown-skip`（contract job 我已在 F13 补上）。

## 修与不修

**未改动任何代码。** 原因：三条修法都涉及超出"机械订正"的判断——

1. **占位 DSN** 应当改成读 `TEST_DATABASE_URL`（并保留一个可用默认），
   还是干脆删掉这些用例、承认它们不属于本 lane？这决定了一批用例的存废。
2. **`anvil_test.go` 的 tag** 应当并入 `test.yml`（去掉 tag，或给该步加 tag），
   还是给 `ci-integration` 的 e2e job 补 Foundry？两者都会改变 CI 时长与额度占用（对应 F23 预算）。
3. **`evm-e2e` lane 到底跑哪一套**——Go 套件、docker 脚本、还是 `make multianvil`——
   需要与 §7 的 lane 表对齐后决定，而不是我把三套都挂上去。

记为 **D16**。
