# T08 交付：SIWE nonce 原子消费与地址绑定

> 对应任务：`docs/specs/2026-10-12-web3-go-backend-delivery-plan.md` §5 的 **T08 / P0 / 8h**。
> 状态：**In Progress** —— nonce 的**原子 compare-and-consume + 地址绑定**已完成并用真实 Redis 验证；
> 其余访问边界（origin/URI/chain/version/time 严格校验、清理循环受 context 管理、operator RBAC、限流、错误脱敏）未做。
> 日期：2026-10-12，Asia/Singapore。

---

## 1. 缺陷

`pkg/siwe` 只有 `GenerateNonce` 与 `VerifySIWEWithOrigin`，**没有任何 nonce 存储**：调用方自己传 `nonceValidator func(string) bool`。因此：

- **没有原子性**：`nonceValidator` 是"检查"，删除/标记由调用方另行完成 ⇒ **check-then-act 窗口**（TOCTOU）。两个请求可以都观察到 nonce 有效。
- **没有地址绑定**：一个 nonce 只与自身绑定，不绑定"发给谁" ⇒ 拿到别人 nonce 的地址也能用。
- **没有共享存储**：多实例部署下各进程各有一份状态，天然无法保证"一次成功"。

T08 的验收正是："**同 nonce 两实例 100 并发只成功一次**"。

## 2. 实现

`pkg/siwe/nonce_store.go`（新）：

### 2.1 `NonceStore` 端口

```go
type NonceStore interface {
	Issue(ctx, address, nonce string, ttl time.Duration) error
	Consume(ctx, address, nonce string) (bool, error)
}
```

`Consume` **原子地**删除 nonce **当且仅当**它仍绑定到该地址。未知/已消费/过期/绑定他人**一律返回 `false` 而非错误** —— 调用方无法借错误区分"地址不对"与"已用过"。

### 2.2 两个实现

| 实现 | 适用 | 关键点 |
| --- | --- | --- |
| `MemoryNonceStore` | **单实例** | 互斥锁保护"读-删-比较"，**先删后比**：失败尝试也会**烧掉** nonce |
| `RedisNonceStore` | **多实例** | **Lua 脚本**在一次往返内完成 `GET` + `DEL` + 比较 |

Redis 脚本是核心：

```lua
local stored = redis.call('GET', KEYS[1])
if stored == false then return 0 end
redis.call('DEL', KEYS[1])
if stored == ARGV[1] then return 1 end
return 0
```

比较与删除分开写，正是本任务要关掉的 check-then-act 窗口。

**其他语义**：地址**大小写不敏感**（校验和格式与全小写视为同一地址）；`ttl` 由存储层强制；空地址/空 nonce/非正 ttl 一律拒绝。

## 6. 接线完成（2026-10-13，提交 `2ef98d7`）

第 5 节列的"**清理 goroutine 没有停止接口**"与"**接线**：`NonceStore` 尚未接进 SIWE 验证路径"两项已完成。**根因不是缺存储层，而是存储层没被用**：`pkg/plugins/api/siwe_handler.go` 自己维护一份进程内 map，验证走 `nonceValidator func(string) bool`。

### 6.1 改动

| 位置 | 之前 | 之后 |
| --- | --- | --- |
| `pkg/siwe` | 只有 `VerifySIWEWithOrigin(opts, sig, nonceValidator)` | 新增 **`VerifySIWEWithStore(ctx, opts, sig, store)`** |
| `pkg/plugins/api/siwe_handler.go` | 自有 `SIWENonceStore`（`Get` 然后 `Delete`，两步） | 依赖 **`siwe.NonceStore` 端口**；`WithNonceStore` 注入共享存储 |
| `challenge` | `nonceStore.Store(nonce, addr)` | `nonceStore.Issue(ctx, addr, nonce, ttl)`；**存储写失败则不返回 challenge** |
| `verify` | `Get` 校验 → `VerifySIWEWithOrigin` → `Delete` | `VerifySIWEWithStore`（**原子消费**） |
| 错误响应 | `"SIWE verification failed: " + err.Error()` | 仅返回 `"SIWE verification failed"`，原因只进日志 |
| `SIWENonceStore.cleanupLoop` | 后台 goroutine，**无停止接口** | **已删除**；`MemoryNonceStore` 改为 Issue 内**摊还 O(1)** 回收过期绑定（无 goroutine ⇒ 无泄漏） |
| `VerifyOptions` | Domain / URI / ChainID | 新增 **`Version`**；另新增 **Issued At 未来时间拒绝**（容差 5min）；`SupportedVersion()` 导出当前版本 |

**消费顺序是设计过的**：所有**与 nonce 无关**的检查（签名、origin、version、过期）先跑，**nonce 最后消费** ⇒ 被拒的消息不会烧掉一个合法签发的 nonce。反方向由 `Consume` 自己保证 —— **失败尝试也烧掉**（单次使用不可重试）。

### 6.3 反向对照：证明"1 个赢家"不是因为竞态难触发

新测试要证明的不是"它能通过"，而是"**旧的写法通不过**"。`pkg/siwe/nonce_store_atomicity_control_test.go` 的 `TestCheckThenActNonceAdmitsManyWinners` 用**同一套 100 并发模式**打**旧形状**（检查 → 真实 `RecoverAddress` → 删除），并**断言赢家 ≥ 2**：

```
OLD check-then-act shape: 10 winners out of 100 concurrent replays   （8 核，5/5 次稳定复现）
atomic Consume:            1 winner
```

**10 = 每 P 一个** —— 每个 goroutine 在被打断前跑完整个窗口。所以原子路径的"1"是 `Consume` 消掉了竞态，不是竞态太窄。

> 首次测量得到 **0 winners**，原因值得记：屏障只用了 `close(ch)`，某个 goroutine 可能在其它 goroutine 被调度前就跑完 50µs 的 ECDSA 恢复。改为**自旋等到全部 100 个 goroutine 驻留**后才进入临界区，才测到真实的 10。
