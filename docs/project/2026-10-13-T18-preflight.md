## 3. 本轮发现的缺陷与修复

### 3.1 `--required-cases` 门禁**空转**（已修，F13/F21 同类）

**症状**：`verify-tests.py --required-cases test/acceptance/required-cases.json` 在 JSONL 全绿时**返回 0**，看似通过。

**根因**：`required-cases.json` 的 15 个场景（E01–E15）`tests` 数组**全为空占位符**；`verify()` 第 5 节按场景逐个检查其 `tests` 里的名字，空列表导致循环体从不执行 ⇒ **没有任何可失败的断言**。一个不能失败的门禁与"空 suite 假绿"（F13）是同一类缺陷。

**修复**（`scripts/acceptance/verify-tests.py`）：当 manifest **声明了场景但要求 0 个测试**时，显式失败：

```
✗ verification FAILED (1 issue(s)):
  - required-cases manifest requires 0 tests across 15 scenario(s):
    it is a placeholder, so this gate cannot fail
    (fill in the test names, or drop --required-cases)
```

并新增自测 `[PASS] self-test: placeholder required-cases manifest is a failure`。

**影响面**：CI 三个 workflow（`test.yml`/`coverage.yml`/`ci-integration.yml`）目前只用 `--jsonl ... --min-tests 1`，**未传 `--required-cases`**，故本修复不改变现有 CI 结果；它让该 flag 在真正被使用时不再假绿。

#### 6.1.1 冷 cache 复核（§7.3 明确要求"不以 warm cache 成功代替新 checkout 验证"）

第一次新检出构建用的是**共享的** `GOMODCACHE`（热的）——那样不能证明冷 cache 也能建。因此用空 `GOMODCACHE` 重跑：

```
cold GOMODCACHE empty: yes
go.work.sum present before build: NO
build exit=0 elapsed=60s
  79 行输出，全部是 "go: downloading ..."，无任何错误
go.work.sum present after build: yes
```

**两条结论，其中一条**更正**了既有认知：**

1. ✅ `GOPROXY=https://goproxy.cn,direct` 下，**冷 cache 的全新检出 60s 内 build 通过**（`GOPROXY` 由 `goproxy.cn` 提供 sumdb 查询）。
2. ⚠️ **`go.work.sum` 被 gitignore，但它不是"必须手工保留的产物"**：Go 会**自动重新生成**它（上表 build 前 NO、build 后 yes）。此前"离了它 `go build` 会以 82 行 sumdb 错失败"的记录**只在 `GOPROXY=direct` 下成立**——那正是 `AGENTS.md` 警告的"warm cache 下容易漏掉"的同一件事。

### 6.2 §4.7 schema fresh / upgrade / rollback（真实 Postgres）

仓库自带 `test/migration/migration_test.go`（build tag `migration`）就是这条演练，本轮**修好并真跑**。它原本有**三处缺陷，合起来使它在任何 `sslmode=disable` 的环境下根本跑不起来，跑起来也证明不了东西**：

| # | 缺陷 | 证据 |
| --- | --- | --- |
| 1 | `replaceDBName` 在最后一个 `/` 处截断，**连查询串一起丢掉** | 首跑即 `pq: SSL is not enabled on the server`（`sslmode=disable` 被吞掉）；无路径的 DSN（`postgres://host`）也被切错 |
| 2 | `runMigrate` 用**测试进程的工作目录**执行 `go run ./cmd/migrate/` | 报 `stat .../test/migration/cmd/migrate: directory not found` |
| 3 | 断言 `events` / `events_metadata` 表，并**把一次 `down` 当成全量回滚** | 两张表**没有任何迁移创建过**（规范表是 `blockchain_events`；`000010` 是把散落的 legacy `events` **改名**）；且 `cmd/migrate down` **每次只回退一步**，所以"回滚相位"实际只演练了最新那一个迁移 |

修正后的四相位（全部 PASS）：

| 相位 | 动作 | 结果 |
| --- | --- | --- |
| 1 `up_fresh` | 空库跑全部 **12** 个 up 迁移 | `schema_version=12`；**9** 张应用表（`api_keys, blockchain_events, blocks, chain_leases, dlq_events, indexing_state, reorg_jobs, reorg_outbox, webhooks`） |
| 2 `up_again` | **再跑一次 up** | **no-op**：`schema_version` 不变、表集合不变（若 runner 重放文件，无 `IF NOT EXISTS` 的 `CREATE TABLE` 必失败） |
| 3 `down_all` | `down` **×12** | `schema_version=0`、应用表 **0 张** |
| 4 `up_after_rollback` | 重新跑全部 up | 表集合与相位 1 **逐字相同** ⇒ **down 是无损的，回滚可恢复** |

**另一条独立不变量**（F06/I02，且是"重跑单个迁移就会静默破坏"的那条）：`blockchain_events` 的唯一约束列必须是 **`chain_id,block_hash,transaction_hash,log_index`**（`000004` 与 `000009` 管同一个约束名，单独重跑 `000004` 会把它换回 `block_number` 版本）。两处（相位 1 与相位 4 之后）都断言通过。
